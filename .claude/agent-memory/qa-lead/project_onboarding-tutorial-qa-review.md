QA pre-implementation review of `design/gdd/onboarding-tutorial.md` on 2026-09-08 (not yet implemented — doc only). Verdict: **READY WITH FIXES** (not NEEDS REDESIGN — no fatal architecture flaw, but several concrete gaps must close before a programmer implements this correctly the first time).

Verified TRUE by reading code (not just trusting the GDD):
- `newGame(seed, teamKeys, opt)` in `src/engine.js` really does `RNG=mkRng(seed>>>0)` — genuinely deterministic, matches GDD's core claim.
- The old tutorial (`TUT[]`, `tutOverlay()`, module-level `tut`) is confirmed **already dead/unreachable** — `tut` is declared `=0` and NEVER set to a truthy value anywhere except inside `tutOverlay()`'s own click handlers, which only render if `tut` is already truthy. A comment at `client.html` ~3958 confirms this was intentional: "the tutorial used to auto-open over the map and blocked the very first click of a new run. It now lives in CODEX." So GDD decision #1 (delete it) is safe, but this reverses a past deliberate product decision to make tutorial passive/non-blocking — worth a one-line flag to game-designer, not a blocker.
- `scCombat(frozen)`, `scReward()`, `scUnitInfo()`, `bindDrag()`/`doTarget()`/`clickDie()` all exist with signatures matching the GDD's assumptions. Click-path and drag-path genuinely funnel into the same `doTarget()`/`clickDie()` calls, so the step-lock's "accept both input paths via one CSS pointer-events gate" plan is sound.
- `ESC_TO_MENU_SCREENS` is a plain array of screen-name strings; adding `'tutorial'` is simply "don't add it," matches GDD.
- Confirmed no accidental leaderboard submission risk: `META.runs++` happens synchronously at run START (not completion), and `submitRun()` only fires from `onRunEnd()` which only fires when `S.phase==='won'` — for a single mock wave 1 with `opt.mode` defaulting to `'short'` (len=12), winning wave 1 lands in `S.phase==='reward'`, never `'won'`. This must stay implicit in the implementation (mode must not be set to a 1-wave run) — GDD doesn't say this explicitly, should be called out to the implementer.

Concrete gaps found (recommended as "fixes" before/while implementing):
1. `verify.mjs`'s UI-rule check (contrast/tap-target/layout-shift/no-NaN) does NOT auto-discover screens — it drives them explicitly via `devGo(k)` (from `src/devtools.js`) per a hardcoded list. A new `screen==='tutorial'` gets ZERO automatic UI-rule coverage unless someone adds a `devGo('tutorial')` case AND adds it to verify.mjs's screen list. GDD only mentions using `devGo()` to *skip* tutorial for QA, not to jump *into* it for testing.
2. `scTutorial()`'s one-line description ("gọi scCombat(false) với S fixture, rồi append overlay") under-specifies step 6: when the mock enemy dies, `S.phase` flips from `'combat'` to `'reward'`, and only then should `scReward()` be rendered instead of `scCombat()` — mirroring the phase dispatch that `render()` itself already does for the real game. As written it reads like `scTutorial()` always renders `scCombat()`, which would never show the reward screen for step 6.
3. AC list (§8) never states the `TUT_ENEMY_HP` guaranteed-win-in-≤3-turns requirement from §3.4/§4 as a testable acceptance criterion — it's a real Config/Data-type requirement (smoke-check tier) with no corresponding AC bullet.
4. `tools/t_tutorial.mjs` (suggested by GDD) as described only checks *determinism* (same output run twice) — it does NOT separately assert the *content* requirement from §4 ("roll đầu phải có ≥1 mặt dmg + ≥1 mặt utility"). Two runs could agree with each other while both being wrong. Needs a second, independent content assertion.
5. Recommend extracting `needsTutorial(meta)` as a small pure/exported function (like other `engine.js` functions) rather than an inline boolean buried in `enterMenu()` inside `client.html` — this is unambiguously "Logic" story type (BLOCKING unit-test gate per project rules) and a pure function is trivially unit-testable without Playwright/DOM; as currently scoped it would require a heavier Playwright integration test for what is a one-line boolean.
6. Real (but low-severity, out-of-scope-for-this-GDD) finding: `RK` (in-progress run save) is a single global `localStorage` key with **no owner/account scoping**, unlike `META` (which has `.owner`). Two different accounts sharing one device could see stale cross-account run data via `loadRun()`/"Continue" on the menu. Pre-existing gap in `player-accounts.md`'s domain, not introduced by this GDD — flag separately via `/bug-report`, don't fix here.
7. Genuine edge case not covered in GDD §5: sync-push failure (per `player-accounts.md`, pushes are debounced/best-effort and never block gameplay) means a tutorial completed on device A could still show again on a *different* device B if the `tut=1` push never lands before B's next login — distinct from the same-device-refresh case the GDD already analyzes. Low severity (re-teaching once), but not yet written down.
