## Question

`docs/godot-port-inventory.md` §5.2 and §9 (item 3) flag this explicitly as a decision
still owed, not just a content gap: `FACE_POOL` (55 faces in JS, generated by
`tools/gen_faces.mjs`) is 0% ported to Godot. Porting it restores one of the JS game's
two reward axes — the `face` and `rune` reward types, the `casino`/`mutant` events, and
2 shop slots (Gene Mutation). Not porting it is explicitly called "defensible" by the
inventory — but right now nobody has actually made that call; it's a silent gap, not a
recorded decision.

Decide with the user:

- Port FACE_POOL now (Phase 2), defer it to a later phase, or drop it from Godot scope
  permanently (accepting a smaller reward-type surface than JS, forever)?
- If porting: does it reuse `tools/gen_faces.mjs`'s generation logic/output directly
  (same 285-identity-part derivation the Vault system also depends on — coordinate
  with [ticket C](C-vault-import-architecture.md), since both consume `PART_FACES`),
  or does it need its own Godot-side authoring/conversion tool the way relics got a
  `data.js → .tres` converter (architecture plan §6)?
- If dropping/deferring: does anything else in the reward pool need rebalancing to
  compensate for one fewer reward axis, or does the existing `level`/`ascend`/`relic`/
  `reroll`/`hp`/`chaos`/`curse` set already carry the game fine without it?

Unlike Vault (ticket C), this has **no architectural blocker** — it's a scope call plus,
if "yes", a content-authoring pipeline choice. Cheap to resolve once picked up.
