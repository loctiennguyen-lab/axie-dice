## Question

Vault/Import-Axie is an explicit Phase 2 requirement from the user
(`godot-port-active.md`: "Vault/import Axie (Phase 2 theo yêu cầu user)") and currently
sits at 0% in Godot — `MetaState.vault` is an empty array nobody reads.

On the JS side this is a real, non-trivial pipeline (rule spec §6): player enters an
Axie ID → server proxy (`api/axie.js`) fetches real 6-body-part data → `axieToDie()`
(pure function, no RNG/Date/IO — required for server replay-verify) converts the 6
parts into 6 dice faces via `PART_FACES`/`part_faces.js` (285 identity-part signature
faces, generated by `tools/gen_faces.mjs`) → stored in `META.vault` (localStorage, 20
Axie cap, persists across runs). Coherence/purity percentages modify face value and HP
(0.64–0.78× band). Vault Axies can't tier up and are blocked from ranked runs
client-and-server-side, because their dice only exist in client localStorage.

Decide, with the user:

- Where does `axieToDie()`'s Godot equivalent live, and does it stay pure (no RNG/
  Date/IO) the same way — this interacts directly with [ticket A](A-anti-cheat-replay-verify-strategy.md)'s
  replay-verify story, since Vault Axies are already excluded from ranked runs for a
  related reason (dice only exist client-side).
- How does the Godot client reach the same server proxy (`api/axie.js`) — same
  endpoint, same contract, or does this need its own decision now that the client
  isn't a browser?
- Does `PART_FACES`/`part_faces.js` (auto-generated data) get regenerated for Godot as
  `.tres`, or read directly — and does `tools/gen_faces.mjs` need a Godot-side
  counterpart or CI gate the way the relic converter does (see architecture plan §6)?
- Persistence: `META.vault` currently lives in browser localStorage. What's the Godot
  equivalent given `MetaState` is already JSON-file-backed for other persistent data?

This is a genuinely new subsystem for Godot, not a refactor of existing GDScript — size
the answer as an architecture sketch the way `godot-port-rule-spec.md` §6 and the
`mellow-scribbling-mochi.md` plan did for combat, not a quick call.

## Resolution — 2026-09-19

Decided with the user across two sessions, built in four layers so each one was provable
before the next depended on it.

**(a) Conversion.** `godot/scripts/core/axie_to_die.gd` — full port of `axieToDie()` and
its helper chain, PURE (no RNG, no Time, no I/O), gated by `t_axie_to_die` (627 checks)
against output generated from the real `src/engine.js`, not hand-written expectations.

**(b) Preview.** Built from the Axie's GENE STRING with the game's own 3D rig — not by
fetching a PNG from a CDN. Direction pointed out by the user and verified against the
addon's own goldens: 9/10 samples build whole, 54/54 decodable parts resolve. Uses the
vendored addon's `AxieAvatarRenderer`, which already exists for exactly this and which a
first draft nearly reimplemented. `godot/scripts/core/axie_gene_preview.gd` +
`godot/scenes/shared/AxiePreview3D.tscn`, gated by `t_axie_gene_preview` (424 checks).

**(c) Store + screen.** `MetaState.vault_*` (`VAULT_MAX=20`, `VAULT_SCHEMA=2`, stale
records flagged and refused registration), `godot/scenes/vault/Vault.tscn`, and the
ranked block enforced in `RunState.start_new_run()` rather than only in the menu. Gated
by `t_vault` (262 checks).

**(d) Network — DECIDED, NOT YET BUILT.** The user chose: **Godot calls the Axie GraphQL
endpoint directly and bypasses `api/axie.js`.** The proxy serves the LIVE JS build with
real players on it; adding a `genes` field there would be a production change made for a
feature no one is using yet, and the Godot build needs its own network path for export
regardless. Cost accepted: the endpoint lives in two places.

Note for whoever builds (d): the addon's goldens cannot stand in for the API. They carry
real genes but no part NAMES ("Anemone", ...), and `AxieToDie` needs part names. A die
built from goldens would look plausible and be wrong.
